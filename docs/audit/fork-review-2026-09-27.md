# SSO fork and plugin review — 2026-09-27

Baseline: `MaxRink/jellyfin-plugin-sso` at `226ef91ff1d185d798f9f4218a4b726798a638b7` (6.1.0.0, Jellyfin 12).

The compatibility port keeps the existing provider configuration and account model. A separate migration change will introduce explicit identity bindings and ownership of permission grants. Neither change deploys a plugin to a running server.

## Coverage and limits

The [inventory](fork-inventory-2026-09-27.json) records 168 repositories and 585 branch heads, including every repository returned by the archived upstream's paginated fork endpoint, recursively discovered child forks, and repositories found through GitHub searches for Jellyfin SSO, OIDC, OAuth, Authentik and remote authentication. Independent continuations include K0lin, Flowfin, aussierk and Ezeqielle. Searches were cross-checked with web results. Every recorded branch was fetched successfully.

This is a dated inventory of discoverable public repositories, not a claim that private, deleted, unindexed or future plugins were inspected. Branch hashes, root license hashes and commits touching the original `SSO-Auth` directory are retained for reproducibility. Non-ancestor commits are candidates, not proof of missing functionality: many forks carry equivalent patches with different hashes. An empty original-directory commit list says nothing about independent implementations using another directory.

## Already covered by the baseline

The prior consolidation already included native browser handoff, stale-link recovery, subject-keyed OIDC links, authenticated StartLink, provider-bound states, username mappings, SSO-only login, logout redirects, Quick Connect forwarding, device-token login, role-object keys, multiple role paths, data-URL avatars, client-secret Basic authentication, dual-stack provider requests, persisted permission updates, preserved administrator permissions, dashboard navigation and package identity fixes. The existing README acknowledgements retain those sources.

Old framework/package downgrades, release manifests pointing at another maintainer, fork-specific names and logos, removing SAML, disabled TLS verification, proprietary-provider endpoints, and copied build outputs are not improvements to this Jellyfin 12 fork and were not applied.

## Separate models and protocols

The independent implementations were compared for behavior; their whole controllers and configuration files were not overlaid on this plugin:

- **Flowfin:** account approval/expiry, protected secret store, declarative provisioning, generic permission and parental-rating rules, metrics, endpoint pinning and persistent session/logout ownership form a broader model. These need migration and operational review rather than silently replacing the existing configuration.
- **aussierk / Ezeqielle:** provider ownership, verified-email reassociation, role-policy merging and back-channel logout depend on their account/session stores. Their OIDC-only replacement is not a drop-in migration for SAML users.
- **NekoShinobi:** grant-only policy editor, previews and accounts UI use a different permission model. Replacing revocation with additive grants would change security behavior.
- **be-nj:** explicit identity linking and an ephemeral-password bridge have a different session path; existing PKCE, provisioning and Quick Connect capabilities already exist here.
- **scottfridwin:** Authentik-specific configuration, group/rating policy and themed callbacks. The generic provider and role capabilities overlap; parental-rating policy belongs in the model migration.
- **KDNX:** persistent session maximum age uses its own required claims and session store. Client addressing/native-device interoperability are portable; its mandatory identity-provider policy is not.
- **nikarh:** direct Authelia password authentication is a separate authentication protocol, not an OIDC fix.
- **BlackDark / UlysseM:** trusted-header authentication requires a distinct proxy trust boundary and network isolation. It is not enabled as an alternate path around OIDC/SAML validation.
- **mpretzel16:** MIT-licensed independent implementation with explicit links, optional password grant and session ownership. No password-grant or session-store migration is included in the compatibility port.
- **organizr / OAuth-login scripts / SSO UI / VS Code helpers:** external applications, client integrations or development tools, not server-plugin fixes to copy wholesale.

These differences are recorded, not claimed as completed ports. The separate migration PR should be evaluated independently of the compatibility fixes.

## Validation

The .NET build treats warnings as errors. The test suite includes cryptographically signed SAML fixtures, malformed input, reference/algorithm/time/audience rejection, address classification, role handling, password repair/rollback, secret sources, policy management and single-use handoffs. The real Jellyfin/authentik browser harness additionally checks native device identity, preservation of another server's credentials, provisioning and self-service linking. The direct/transitive NuGet vulnerability audit reported no vulnerable packages at the time of the review.

## Upgrade behavior

SAML logins must start at Jellyfin's Start endpoint. Unsolicited responses and raw-assertion calls to Auth/Link are rejected. Identity providers need a current signing certificate, a supported strong signature, a valid expiry, the configured SP audience, and request/recipient correlation. The browser handoff still calls the same Auth route, but sends an opaque single-use value. OIDC handoff values are also distinct from callback states.

Empty-password linked accounts receive an unknown random password; existing nonempty passwords and authentication-provider routing are preserved. Avatar fetches are capped at 5 MiB and public HTTP(S) destinations; inline raster images remain supported. Private-network URLs, SVGs and HTTP redirects are refused. These security restrictions are intentional changes, not opt-in permission changes.

`OverrideDefaultScopes`, custom authorization parameters, external secrets, download permissions and preservation of unmanaged folders are opt-in. Existing account adoption and username mapping remain in the compatibility branch; stricter identity migration is separate.
